How approval-flow changes work

A step-by-step account of what has to change so that reordering approvals, adding approval levels, choosing approvers, and adding fields become configuration instead of code — starting from your codebase exactly as it is today.

verified against the repo · 2026-08-11 4 gaps marked 13 comprehension checks

Each part ends with a check yourself box. Try to answer before opening it — if the answer surprises you, re-read that part rather than moving on. The four parts marked gap are things missing from the plan I gave you earlier, found by comparing it against what Palantir Foundry actually implements.

00

Where you are today

Three separate mechanisms, none of them data.

Before anything changes, be precise about what exists. Everything below was read out of the repository, not assumed.

Order is Python, written twice

# backend/app/services/workflow_unlocks.py:25
def design_unlock_ready(site: models.Site) -> bool:
    return (site.legal_dd_status or "pending") == "positive" and (
        site.finance_status or "pending") == "approved"

# backend/app/services/design_service.py:230
def _assert_design_unlocked(site: models.Site) -> None:
    ...  # the same rule again, raising 422 with per-branch messages

one business rule · two definitions · called from lines 341, 452, 923, 983

So the rule that decides when Design opens has two definitions and five enforcement points. On top of that, the frontend's stateMachine.js mirrors the transition table by hand. Changing the order means editing all of it consistently.

Approval levels are frozen in DDL

-- backend/database/schema.sql:826
status text NOT NULL DEFAULT 'pending_admin_review'
  CHECK (status IN ('pending_admin_review','under_exec_review',
                    'under_supervisor_review','pending_admin_final',
                    'ready_to_launch','launched'))

-- backend/database/schema.sql:729
CONSTRAINT chk_site_budget_status
  CHECK (status IN ('draft','pending_supervisor','pending_admin','approved','rejected'))

Two modules invented two different multi-level approval patterns, both as CHECK constraints. Adding a level to either is a database migration. The third module that needs this will invent a third pattern, because inventing one is cheaper than generalising.

Who approves is implicit

There is no row anywhere saying "level two of the launch approval goes to the module supervisor." It is the shape of the code — whichever endpoint flips the status, guarded by whichever role decorator sits on it. You cannot query it. You can only read the routers.

The cost of one change today

"Design before Finance, with two approvers instead of one" = two Python edits, one migration, a deploy, and an audit of the frontend mirror. Roughly a day, and it lands for every tenant.

CheckWhy is the rule being written in two places worse than it being written in one place badly?

Because the two can disagree, and nothing will tell you. A single ugly function is at least always self-consistent — whatever it does, it does everywhere.

Two copies drift the moment someone edits one. And the failure is silent and asymmetric: design_unlock_ready decides whether the UI shows Design as available, while _assert_design_unlocked decides whether the API allows it. Drift between them means a button that appears and then 422s, or worse, a module that looks locked but isn't.

This is the same class of problem as your three schema files disagreeing 30/29/24 — and it is the entire argument for one rule in one row.

01

Order becomes edges

You already have the edges. They're the mirror columns.

The insight that makes a node editor possible: the mirror columns on sites — legal_dd_status, finance_status, design_status, project_status, is_launched — are completion signals.

An edge Legal → Design is nothing more than the fact that Design's gate mentions legal_dd_status. The graph is already there, encoded in which columns each rule reads.

today · python
Two functions, five call sites. Changing the order = editing both, consistently, then deploying.
after · one row
action_type.preconditions — one JSON value, edited with an UPDATE. 
{"and": [
  {"==": [{"var": "legal_dd_status"}, "positive"]},
  {"==": [{"var": "finance_status"},  "approved"]}
]}

design.open — the rule from design_service.py:230, as data

To put Design before Finance you rewrite two rules: Design drops its finance_status clause, and Finance gains a design_status clause. That is the entire operation.

Why there is no flow_edges table

The graph is derived, not stored. Drawing it means reading the preconditions; editing a node means rewriting them. A separate edge table would be a second source of truth that could disagree with the rule actually enforced at runtime — reintroducing, one layer up, exactly the drift problem this whole exercise is meant to remove.

CheckA colleague proposes storing the graph in flow_nodes and flow_edges, and generating the preconditions from it. What breaks?

Nothing, until someone writes a precondition the graph cannot express — and they will, on about week three. "Design opens when legal is positive and the site is under 1500 sqft" is a perfectly reasonable rule with no edge to represent it.

Now the graph is an incomplete picture of the truth. Either you forbid such rules (crippling the feature) or you accept a designer that silently doesn't show everything that governs the flow — which is worse, because people will trust it.

Deriving the graph from the rules means the picture is always a faithful, if sometimes partial, view. Deriving the rules from the graph means the graph becomes a cage.

02

Levels become rows

Preconditions say when a module starts. Not how many people sign off inside it.

This is the distinction most easily missed. A precondition is a single boolean over the object's fields. It has no concept of "first the supervisor, then the admin." That needs the one new table this design adds.

CREATE TABLE ontology.approval_step (
  id            uuid PRIMARY KEY,
  version_id    uuid NOT NULL REFERENCES ontology.ontology_version(id),
  action        text NOT NULL,   -- 'launch.approve'
  seq           int  NOT NULL,   -- 1, 2, 3 …
  label         text NOT NULL,   -- 'Supervisor review'
  status_value  text NOT NULL,   -- what the record sits in awaiting this level
  assignee_rule jsonb NOT NULL,  -- part 03
  on_reject     text,            -- which status to fall back to
  UNIQUE (version_id, action, seq)
);

launch_approvals' six-value CHECK becomes four rows. The status values are now generated from rows rather than constrained by DDL. Adding a level is an INSERT; removing one is a DELETE.

How to migrate without breaking anything

Do not drop the CHECK constraints on day one. The safe order is:

  1. Add approval_step and populate it to describe the chains that already exist
  2. Have the services read the chain from the registry, still writing the same status strings
  3. Confirm behaviour is identical — the existing CHECK now acts as a safety net
  4. Only then relax the constraint, and only for modules a client actually needs to vary

Step three is the one that matters. If the registry ever generates a status the CHECK rejects, the write fails loudly instead of quietly corrupting an approval chain.

CheckWhy keep the CHECK constraint during migration when the whole point is to get rid of it?

Because during the transition you have two systems claiming to know the valid statuses — the old DDL and the new rows — and you need to find out if they disagree before you trust the new one.

The constraint costs nothing while they agree, and the moment they don't, it converts a silent data-corruption bug into a loud failed write with a stack trace. That is precisely the trade you want while migrating something that governs money and legal sign-off.

Drop it only per-module, and only once a client genuinely needs a chain the constraint forbids.

03

Assignees

Who signs each level — a small, closed vocabulary.

Each step carries an assignee_rule. The important property is that it maps onto machinery you have already built:

RuleResolves toExisting mechanism
{"kind":"role","role":"supervisor","module":"design"} Design supervisorsuser_module_memberships
{"kind":"role","role":"business_admin"} Tenant adminsbusiness_admins
{"kind":"object_field","field":"supervisor_id"} This site's supervisorsites.supervisor_id
{"kind":"site_delegation","module":"design"} The per-site delegatesite_delegations

That last row matters. You built per-site, per-module delegation with grant and revoke already. It stops being a special case bolted onto each module and becomes one approver kind among four.

The observer role must be excluded

rbac/roles.py defines four roles, not three: business_admin, observer, supervisor, executive. An observer reads everything and writes nothing — enforced in app/core/deps.py, not in the guards. An observer must therefore never resolve as an assignee, or you create an approval step that nobody can ever complete. This needs an explicit exclusion in the resolver, not an assumption.

CheckWhy must assignee_rule stay a closed vocabulary rather than becoming a general expression language?

Two reasons, and the second is the one that bites.

It must be invertible. You don't only ask "is this user the assignee?" — you also ask "whose queue does this appear in?" and "who do we email?" A closed set of four kinds can be resolved forwards into a set of user ids. An arbitrary boolean expression can only be evaluated per-candidate, so building a queue means testing every user in the tenant against every pending record.

It has to be auditable. "Who could have approved this?" is a question a client's auditor will ask. A closed vocabulary answers it with a query. An expression language answers it with a shrug.

When routing genuinely needs computation, that is a function_ref — named code, tested like code — not a bigger rule grammar.

04

Fields

Add and rename columns per client, without a migration.

A different mechanism from the flow, but the same principle. Today, adding a field means: migration → SQLAlchemy model → Pydantic schema → router → API client → form → table column. Seven files, a deploy, and it lands for every tenant whether they want it or not.

INSERT INTO ontology.property_def
  (version_id, object_type, api_name, display_name, type, storage, column_name)
VALUES (qsr_overlay, 'Site', 'franchiseRoyaltyPct',
        'Franchise Royalty %', 'decimal', 'props_json', 'franchise_royalty_pct');

storage carries the whole design:

storageWhere the value livesWhen to use it
columnA real typed column Every base property. Fast, indexed, constrained
props_jsonA key in one props jsonb, GIN-indexed Client-specific additions. No migration
derivedRecomputed by the runtime The mirror columns become these

Renaming is the same row with a different display_name. The physical column never moves, so nothing breaks — expected_rent stays expected_rent on disk; tenant B just sees "Base Rent".

Overlay authority is add and rename only, never remove. A client who could delete a base property would break your own applications.

The escape hatch that keeps it fast: when a client starts filtering hard on a props_json field, promote it — same api_name, storage flips to column, backed by a real generated column. Nothing above the registry notices. No EAV table, ever — that would defeat the query planner and your constraints.

CheckIf props_json needs no migration and works fine, why keep column at all? Why not put everything in JSONB?

Three things you lose, in increasing order of pain.

Type safety. props->>'x' is always text. Every numeric comparison becomes a cast, and a bad value fails at read time rather than write time.

Constraints. Your schema is full of real integrity — CHECK (legal_dd_status IN (…)), foreign keys, UNIQUE (site_id, phase). None of that exists inside a JSONB blob. You'd be moving integrity from the database into application code, which is exactly the trade that makes triplestores unusable for this.

The planner. A GIN index answers containment well, but it cannot do a range scan or drive a sensible join order. On a tenant with 40 sites nobody notices. On one with 40,000, a report that touched five JSONB fields becomes a sequential scan.

Hence the rule: core properties that every client has are real columns; overlay properties start in JSONB and get promoted when usage proves they matter.

05

What actions actually dogap · critical

The hole in the plan I gave you. Everything else leaks through it.

Everything up to here declares when an action may run. Nothing declares what it does.

In my earlier plan, action_type holds a gate and then hands off to a hand-written Python service to perform the mutation. So you would have config-driven reads and config-driven gates sitting on top of hand-written writes.

This breaks the test that governs the whole sequence

The exit test for the packaging stage reads: "ship a new object type using only config; if it needs one hand-written router or service function, this stage is not done."

With writes still hand-written, that test cannot pass. A new SiteInsurancePolicy would still need someone to write its create-and-update service by hand — which is the exact cost the platform exists to remove.

Foundry's action types declare parameters and rules — modify this property, create this object, create this link, delete — so the platform can execute a write it has never seen. That is what's missing:

action_param(action_type_id, api_name, type, required, default_expr, options_query)

action_rule (action_type_id, kind, target, value_expr)
  kind ∈ modify_object | create_object | create_link | delete_object

Plus one generic endpoint — POST /actions/{name}/apply — that validates parameters, evaluates the gate, then walks the rules inside your existing lock → mutate → audit → notify runtime. The runtime does not change. It gains a generic caller.

Cost: roughly 6–8 weeks, and it belongs between the properties/links work and the client-database work. Discovering this at the packaging stage would mean re-opening two earlier stages.

CheckYour existing write path is already correct — lock, mutate, audit, notify. Why does a generic write path not put that at risk?

Because the runtime is not what becomes generic. The caller is.

Today a service function decides "set design_status = 'approved'" and calls the runtime. Afterwards, a rule row says modify_object(design_status, 'approved') and a generic executor calls the same runtime with the same lock, the same audit write, the same outbox enqueue.

What changes is where the instruction comes from — a Python literal becomes a row. What must not change is that there is still exactly one write path, still row-locked, still audited. If the generic executor ever bypasses that runtime to write directly, you've lost the single property that makes the whole architecture trustworthy.

06

Change controlgap

You're about to let clients edit production rules. With no review step.

My plan gives ontology_version a draft/published status and stops there. That is not change control — it's a flag.

Foundry's answer is a proposal: branch the ontology, make changes, merge checks run, an editor of each affected resource approves, then publish. A pull request for the ontology.

Without it, a tenant admin dragging a node in the designer is editing production. No diff, no review, no "what does this break", no rollback. The first time someone reorders Legal below Design on a live workspace with forty sites in flight, you will want all four.

This is not decoration. It is the thing that makes an editable flow safe, and it has to land with the designer UI, not after it. Roughly 3–4 weeks.

CheckWhat should a merge check actually verify before an ontology change is allowed to publish?

At minimum, four things — and each maps to a failure you'd otherwise ship:

Every precondition is a well-formed object. A rule that isn't an object is a truthy literal, which means an always-open gate. This check alone justifies the mechanism.

No dependency cycle, and nothing waits on a module that runs later. The designer already validates this live; publish must enforce it.

Every rule references properties that exist on the object type in this version. Rename a property and any rule mentioning the old name silently evaluates null — and null == "positive" is false, so the gate quietly locks shut forever.

No approval step resolves to an empty assignee set. A step nobody can complete is a permanently stuck record, and you'll hear about it from the client, not the tests.

07

Records already in flightgap · hardest

The question nobody asks until it has already happened.

A client changes their approval flow at 2pm. Forty sites are mid-approval. What happens to them?

This is not a primitive, which is why it's absent from every plan I've written you. It is the hardest operational problem in the whole design, and there are only three answers:

ApproachWhat happensThe cost
Stamp and freeze Each record carries the ontology_version_id it started under and finishes on the old flow You now run N flow versions at once. Every queue, every dashboard, every notification template must be version-aware
Migrate Move in-flight records onto the new flow Needs an old-status → new-status mapping, and it is genuinely ambiguous. A site sitting in pending_supervisor when that level is deleted goes where — forward unapproved, or backward?
Freeze edits No flow changes while anything is in flight Simplest, and useless — something is always in flight
Why this hurts you more than it hurts Foundry

Foundry's actions are mostly point edits — submitted and resolved in seconds. Yours are multi-day approval chains that sit in a queue. Your workflow is precisely the case where a mid-flight definition change is most likely and most damaging.

My recommendation: stamp-and-freeze, with the version pinned at record creation, plus an explicit admin-triggered migration that previews what moves where before committing. But it has to be designed before the designer ships, because pinning a version onto every record is a data-model decision, not a feature you add later.

CheckUnder stamp-and-freeze, a supervisor opens their queue. Two sites need approval — one on flow v1, one on v2, with different level names. What does the queue show?

This is the question that reveals the real cost, and there is no free answer.

The queue cannot show one column of statuses, because pending_supervisor in v1 and pending_review in v2 may be the same human step under different names — or genuinely different steps. So the queue has to resolve each row's label through the version that row is stamped with, not through the tenant's current version.

Which means every read surface — queue, dashboard, notification template, exported report — takes the ontology version as an input rather than assuming "the current one". That is a real, pervasive cost, and it is the honest reason people reach for "migrate" instead, then discover migration is ambiguous.

If you take one thing from this part: decide it before you ship the editor, because both answers are expensive and only one of them is expensive later.

08

Column-level securitygap

Row visibility is planned. Property visibility isn't.

The policy compiler decides which rows a caller sees. Foundry also secures properties, and renders an unauthorised one as null rather than failing the request.

You hold commercial rent, revenue-share percentages, escalation schedules, and per-client financials. "This executive can see the site but not its rent" is a real requirement you will meet at client #2. The table is already sketched in your V3 registry — security_policy with scope='column' — it simply isn't in any stage. Roughly 2 weeks, extending the policy compiler rather than adding a new system.

CheckWhy render a forbidden property as null instead of returning 403?

Because a 403 leaks the thing you're protecting. If requesting a site returns 403 whenever it has a rent value, the caller learns which sites have rents — and often that is the sensitive bit.

It also makes the API unusable. A list of forty sites where two have restricted rents would fail the entire request rather than returning thirty-eight usable rows plus two with a blank field.

null is uniform: the caller cannot distinguish "no value" from "not permitted", the response shape stays stable, and the UI renders a dash. Foundry made this choice deliberately and it's worth copying exactly.

09

What runs at request time

The ordering is not cosmetic.

lock the row          SELECT … FOR UPDATE  (fetch_site_for_update_or_404, _common.py:79)
  ├─ 1  lifecycle     is the object in a status where this action exists?
  ├─ 2  identity      required_role / required_module
  ├─ 3  parameters    validate the submitted payload
  ├─ 4  preconditions the JsonLogic gate
  ├─ 5  approval step is the caller the assignee for the current seq?
  ├─ 6  apply rules   modify / create / link  (part 05 — not yet built)
  ├─ 7  recompute     derived and mirror columns
  ├─ 8  audit         audit_logs + stage_events
  └─ 9  notify        notification_outbox

Two things to get right

The gate must be evaluated inside the lock. If it runs before SELECT … FOR UPDATE, two concurrent requests can both read finance_status = 'approved', both pass, and both mutate. Today this is safe by accident, because _assert_design_unlocked(site) receives a site already fetched under lock. Extracting the gate into a generic evaluator makes that coupling easy to lose.

Checks 1, 2 and 4 fail differently and must respond differently. A lifecycle failure means the button should never have rendered. An identity failure is a 403 that must not explain the workflow to an unauthorised caller. A precondition failure is a 422 that should explain exactly what is missing, because it is your own user's next action.

CheckWhy is identity checked at step 2, before the precondition at step 4 — rather than after?

Because the precondition's error message is informative by design. "Design is gated on Finance approval" is exactly what your own user needs, and exactly what an unauthorised caller should never receive.

Check identity first and an outsider gets a flat 403 that reveals nothing about your workflow. Check it after, and you've handed them a description of your approval process, one probe at a time.

The general rule: order your checks so the least informative failure fires first.

11

What you don't need from Foundry

Most of it. That's what makes this attemptable.

The missing-features list is long, and it is important to be specific about how much of it is irrelevant to you:

  • Pipeline Builder, Code Repositories, transforms — your data arrives via connectors and mapping, not a transform DAG
  • Object Storage V2 and the object data funnel — a separate index layer over Postgres is unjustified at 27 tables and sub-million rows
  • Workshop fidelity — you need one config-driven object view and form renderer, not a drag-and-drop app builder
  • Vertex, Map, Machinery, Foundry Rules — different products, different problems
  • Marketplace's cryptographic signing — copy the API-name-consistency rule, skip the signing infrastructure until someone asks for it
  • OSDK in three languages — TypeScript for your own frontend is enough; add Python and Java when a third party signs

That is most of Foundry's surface area. Skipping it deliberately — because you ship one vertical rather than a general modelling tool — is the reason a small team can attempt this at all.

12

Final self-test

If these four are comfortable, you have the model.

1A client asks: "can we make Design need two approvals and happen before Finance?" Which rows change?

Order — two action_type.preconditions values. design.open drops its finance_status clause; finance.open gains a design_status clause.

Levels — one new approval_step row for design.approve at seq=2, with its assignee_rule and status_value.

All of it on the client's overlay version, leaving every other tenant untouched. Then — and this is the part that is not yet built — a proposal, merge checks, and a decision about the sites currently sitting in Design under the old chain.

2Why does a corrupted precondition row fail open rather than closed, and what stops it?

JsonLogic treats anything that isn't an operator object as a literal. apply(5) returns 5; apply("…") returns the string. So a rule that round-trips out of the database as a JSON string instead of an object evaluates to a truthy value — and the gate permits everything.

A malformed Python if raises. A malformed rule row permits. That asymmetry is the tax for moving logic into data.

What stops it: the evaluator type-checks and refuses any non-object rule; the tests assert the rule's shape rather than only its verdict; and a merge check validates every rule before publish. You gave up the compiler — you have to replace it with a validator.

3Which single missing piece would make the packaging exit test impossible to pass, and why?

The generic write path — part 05.

The test says a new object type must ship using only config. With reads generic and gates generic but writes still hand-written, every new object type still needs someone to author its create-and-update service by hand. That is precisely the cost the platform exists to remove, so the test fails by construction.

It is the one gap that must be closed before the later stages, because discovering it at packaging time means re-opening the properties and links work.

4Your only client is Blue Tokai. Is any of this worth building right now?

Mostly no — and that is the honest answer.

For a single tenant with one flow and one vocabulary, the registry is indirection bought for flexibility nobody uses. The value starts at client #2 and compounds from there. So the real question isn't technical: it's how close that second client is.

The exceptions are genuine. Stage A collapses a rule that today has two definitions and five call sites — worth doing as ordinary maintenance. Stage B closes a row-level security gap that exists in production right now, whatever happens to the platform idea.

The failure mode to avoid is building the registry and continuing to hardcode alongside it, paying for both. The forcing function is the packaging exit test: until a new object type ships config-only, the registry is cost with no return.
